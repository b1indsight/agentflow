AGENTFLOW / 系统架构

一次交付如何完成

从打上 flow 标签的 Issue 或控制台任务开始：控制端记下要做的事，工作端修改代码，GitHub 保存推送的提交和 PR。

01 / 交付边界

分支已推送，PR 就开好了吗？

  1. Flow 是持续跟踪的任务。一次开工称为 Attempt；其下可以有多个执行步骤（Job）。
  2. 首轮调用 flow.open_pr 时，控制端先核对分支并保存交付意图。收到匹配的执行结果后，才创建或认领 PR。
  3. 评审修订沿用这一轮的分支和 PR。控制端用 webhook 和主动查询核对已追踪 PR；归档后重新开工会产生新的 Attempt。
02 / 恢复边界

工作端断线，谁能接着跑？

  • 同一身份的工作端重连，核对任务凭据与原工作区；结果若已生成，可以重送，控制端按持久记录继续处理。
  • 能证明没有启动、没有待确认停止的任务，租约过期后才可重新排队。可能已执行但无法确认的任务过了恢复期限会被阻塞。
  • 断线、归档或结果入库本身都不能证明旧进程已经停止。回收旧执行并确认清理后，工作区才可安全复用。
03 / 对照实例

同一项需求，在三端分别能看到什么？

假设你提交了「导出报表时支持按日期筛选」。任务编号是 42，首轮编码交给工作端 A。下面四个片段分别截取这次工作在不同条件下的一个时刻，编号和仓库内容都是示例。展开片段，可以看到应以哪一侧的记录为准，以及另一侧为什么可能暂时没有结果。

控制台已经返回任务编号，GitHub 上还没有 PR

先看控制端。浏览器向控制台提交任务，控制端重新核对 GitHub 安装和目标仓库，再让工作流服务登记 Flow、首次开工和编码作业。这些记录在同一笔数据库事务里提交。此时页面可以展示任务；即使工作端 A 正在忙，用户也不需要重复创建它。

GET /api/flows/42
id: 42          lifecycle: queued
pr_number: null

这里只摘取详情响应的三个字段，并非完整的 JSON。编号指向可以继续查询的业务记录；排队表示控制端仍在安排工作。创建任务与打开 PR 发生在不同阶段，因此没有 PR 编号不能说明创建失败。若要知道 A 是否已经领到作业，应查看这个 Flow 的 Job 记录。

工作端已经推送提交，评审者在哪里找 PR？

先区分 Git 推送和 PR 创建。工作端在已绑定目录里运行编码工具，修改和测试通过后可以把版本推到目标分支。GitHub 此时已经能展示分支差异；评审者通常需要的却是带标题、说明和讨论记录的 PR。这是后来由控制端负责的另一项操作。

首轮编码工具向控制端提出 flow.open_pr 请求时，工作流先核对推送的分支并保存交付意图。工作端随后交回与这次意图相符的执行结果，控制端核验后才向 GitHub 创建或认领 PR。若创建请求已经送达但应答丢失，直接重发可能产生重复的远端操作。控制端要先按仓库和分支核对远端状态，不能凭本机进程已经退出就向用户报告成功。

读者可以这样核对：从任务详情里的交付链接打开当前 Attempt 对应的 PR；若只能看到分支，先确认结果是否已由控制端接收。手动新建一张同名 PR 会改变核对现场，不能作为排查的第一步。

控制端重启，工作端 A 上的编码进程还在运行

先保留原执行现场。WebSocket 断开只切断了两台机器的消息传输。本机工作区仍可能有未提交的修改，编码进程也可能正等一个工具回复。新的控制端能从数据库读出原 Job 的分配，但不能从一条离线状态推断进程已经停止。

原工作端重连后会报告自己保留的执行记录。控制端核对 Job、工作端身份和分配凭据；若原执行还活着，就让它接回通信。若原执行已经结束并留下最终结果，就让它补传结果。另一个工作端 B 即便能克隆同一仓库，也没有 A 的分配凭据和本地记录。让 B 重新编码既可能覆盖未交付的工作，也不能解释 A 稍后交回的结果。

对照图 02：如果断点位于第一与第二个确认点之间，A 应补传本机保存的结果；若数据库早已收妥结果，控制端可以继续核验交付。两条恢复路径处理的都是原 Job。控制端替换测试让连接在编码期间真实断开，再检查同一个编码调用最终只交付一张 PR。

已经进入 review，为什么任务仍在等我回答？

看交付状态和问题正文。编码工具可能已经理解了「按日期筛选」，但无法自行决定以用户时区还是 UTC 划分一天。这时可以请求人工输入。控制端记下问题，保留 Flow 及本次开工的归属，供用户回到详情里回答。进入需要评审或人工参与的阶段，并不要求仓库里已经有一张 PR。

假设你回答「全部使用 UTC，以跨午夜的一条记录做测试」。控制端可以先把这句话保存下来。页面显示消息已记录，说明网络请求成功传到了控制端；原工作端是否已经收到、编码工具是否采用要求、GitHub 是否已经出现新的测试，分别要从后续的作业、会话和提交核对。只见到第一项时，重复发送同一句话不能证明后面三项已经完成。

如果后来要追查「哪一次开工回答了这个问题」，使用 Flow 编号查整项工作，再对照当前 Attempt 与 PR。重新开工会保留同一个 Flow 的历史，但产生新的一次执行归属。旧 PR 上已有的答复有助于理解背景，不能替代新一轮交付记录。
