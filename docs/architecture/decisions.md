# 三个容易混淆的完成时刻

一项任务可能同时显示「PR 已合并」「Flow 已归档」和「工作区仍在收尾」。这三条记录看起来矛盾，其实分别回答了三个问题：GitHub 上发生了什么？用户的工作是否已经结束？执行代码的机器是否安全空闲？AgentFlow 把这些问题分开回答，原因可以从三个常见的中断说起。

## 一、代码已经推送，但 PR 还没有创建

工作端负责改代码和推分支；控制端持有 GitHub App 身份，负责创建 PR。若工作端刚推送就断开连接，仅凭分支存在，控制端无法知道这是最终交付，还是编码者打算继续修改的中间提交。首轮因此要求明确选择：申请开 PR，或者留言请求人来决定。搜索同仓库任务是只读操作，不代表完成了上述任一种交付。

申请开 PR 时，工作端核对工作区、指定分支和远端提交；控制端结合工具调用记录、最终结果和 GitHub 上观察到的提交，才能创建或复用 PR。这份交付属于**当前 Attempt**。同一次修订继续用原 PR，不接管同名的无关分支，也不强推覆盖别人的修改。见[工作端核验](../../app/worker/execution/vcs.py)、[控制端工具](../../app/controler/workflow/tools.py)和[首轮交付走查](../feature-walkthroughs/first-delivery.md)。

## 二、对方做完了，但回信在路上丢了

假设控制端已向 GitHub 发出评论，随后连接超时。直接重发，可能让评审者收到两条完全相同的回复；直接标记成功，又可能让一条没发出的回复永远消失。[结果处理模块](../../app/controler/workflow/results.py)先把要执行的操作保存下来。[远端操作模块](../../app/controler/workflow/effects.py)恢复时按分支查 PR，或按作者和稳定标记查找已发评论。仍无法证明结果时，保留未决记录。人的「重试」也不等于授权再发一遍。

控制端和工作端之间也会丢回信。工作端把已知的最终结果写在[本地执行记录](../../app/worker/state/execution.py)里，重连时可以再传一次；控制端从已持久接收的结果继续处理。不知道一个命令是否跑过时，却不能换一台机器把它再跑一遍。这就是为什么租约或者心跳超时后，系统有时宁可让任务受阻。编码进程的超时还有另一层含义：限制的是连续没有标准输出或错误输出的时间，不是整项工作的总时长，见[空闲计时](../../app/worker/execution/idle.py)。

## 三、人的工作结束了，机器还没有交还目录

确认当前 PR 已合并，控制端可以立即记录成功归档。原 worker 可能恰好离线；即使收到停止指令，本机进程也可能仍在退出。直到收到停止证据、需要核对的外部操作也已处理，才可以释放绑定。此时重新开工才不会误用仍在写入的目录。见[生命周期处理](../../app/controler/workflow/lifecycle.py)和[归档走查](../feature-walkthroughs/continuation.md)。

目录归属解决的是调度冲突，并不提供操作系统级的隔离。工作端使用限时、限仓库的推送授权，不接收 App 私钥；更新 skill 仓库使用独立的只读授权。Codex 和 Amp 当前拒绝受限的执行配置，运行者仍需用专用账户、容器或虚拟机保护控制端机密。不要把两项工作分配到不同路径就视为可以安全接入不互信的租户。详见[凭据注入](../../app/worker/execution/credentials.py)、[执行权限](../../app/worker/execution/permissions.py)和[部署说明](../deployment/README.md)。
