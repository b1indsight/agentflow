# 自动创建仓库标签 — Feature record

**Stage:** Implementation — 独立发布分支验证完成，结果见 [003]；尚未部署或执行真实 App 写入验收。
**PR:** 准备发布至 `main`；独立工作区保留源工作区的其他改动。
**Bookmark:** `feat/repository-label-bootstrap`

## 1. Initial plan

### 背景与目标

用户希望系统自动建立使用所需的三个仓库标签，省去部署时的人工准备。
当前 [部署说明](../deployment/README.md#L39) 要求预先创建 `flow`、`flow:in-review`、
`flow:done`；[标签写入](../../app/github/issues.py#L107) 只检查定义，不创建。
[事件路由](../../app/controler/events/router.py#L37) 没有 installation 接入处理，
[启动流程](../../app/controler/runtime.py#L137) 也没有发现仓库或初始化标签的后台任务。

目标是在用户首次给 Issue 添加触发标签之前，自动补齐仓库中的标签定义。
用户提出“实现这个”已明确功能方向；本记录进一步确定发现范围、执行时机和错误处理，待批准后实施。

### 范围与验收标准

1. 覆盖 GitHub App 安装授权范围内的所有可访问仓库，包括从未运行过 Flow 的已有仓库；
   跳过暂停的 installation 和已归档仓库，不改变 App 安装范围或权限。
2. 使用 `trigger_label`、`in_review_label`、`done_label` 的实际配置名称；沿用
   [非空、忽略大小写互不相同的校验](../../app/controler/config.py#L107)。
3. 只创建缺失定义，保留已有标签的名称、颜色和描述，不 PATCH、删除或重命名任何标签。
4. serve 启动后立即在后台扫描，此后按现有 `reconcile_interval_seconds` 周期扫描，
   默认 300 秒。新安装或新授权的仓库在下一轮发现；不需要重装 App 或重新发送 webhook。
5. 单仓库权限错误不影响其他仓库；记录明确、脱敏的诊断。限流遵守 Retry-After，
   初始化失败不阻止 Webhook 接收、worker 连接或本地数据库 readiness。
6. 重复扫描、重启、并发创建和创建响应丢失不会覆盖已有定义；下一轮重新读取远端事实再补齐。

本次只建立仓库 label 定义，不自动给任何 Issue/PR 添加触发标签、不启动 Flow。
不新增配置开关、依赖、数据库表、wire protocol 或通用持久任务账本。
保留现有 Issue/PR 增量 add/remove 行为及结果恢复机制。

### 拟议行为

后台枚举 App 的 installation，再枚举每个 installation 可访问的仓库，完整处理分页。
逐仓库读取标签列表，只有完整读取成功后才判断缺失并创建；列表请求返回 404 或权限错误
视为读取失败，不把不可访问的仓库当作“没有标签”。

新建标签按角色使用以下默认值；名称始终来自实际配置，已有标签不采用这些默认值：

| 角色 | 默认名称 | 颜色（不含 `#`） | 描述 |
|---|---|---|---|
| 触发 | `flow` | `5319e7` | `Start a FlowTool task` |
| 审核 | `flow:in-review` | `fbca04` | `FlowTool delivery awaiting review` |
| 完成 | `flow:done` | `0e8a16` | `FlowTool task merged and archived` |

标签身份使用忽略大小写的名称匹配。已有 `Flow` 而配置为 `flow` 时保留原名称；
触发和取消路由同步按忽略大小写比较，避免保留已有标签后无法触发。
不会修改 allowlist、bot 过滤、取消授权或其余事件处理规则。

创建遇到 422 时重新读取目标标签：只有确实存在匹配名称才能视为并发创建成功，
否则保留验证错误。超时、5xx 或断线不盲目重发写请求；下一轮先重新读取列表。
429/限流停止当前扫描并延后下一轮，采用现有 `retry_delay` 计算等待时间；
其他仓库级失败记录仓库、标签（如适用）、kind、status 和 request ID 后继续其他仓库，
下一轮再尝试。不保存或打印 token、私钥、上游原始错误 body。

### 技术设计与受影响模块

- `app/github/apps.py`：为 `GitHubApp` 和 `Installation` 增加分页枚举 installation、
  repository 的操作，继续分别使用 App JWT 和 installation token，不引入全局客户端。
  暂停和归档信息来自实际响应；资源操作继续由相应身份拥有。
- `app/github/repositories.py`：增加仓库级标签补齐操作，接收明确类型的名称、颜色和描述。
  分页读取全部仓库标签后只创建缺失项；并发重复创建通过查询核实，不全量覆盖标签。
  查询和写入均关闭 SDK 自动重试，由后台循环负责恢复，复用 `translate_errors`。
- 新增 `app/controler/reconciliation/labels.py`：负责三个角色的定义、扫描和失败隔离。
  先采用顺序流式遍历，不全量堆积仓库、不新增并发池或成功缓存。
  枚举分页和单仓库处理作为有界单元，接入现有 `MaintenanceStore.activity`；
  维护暂停后不开始新单元，等待和退避不占用 activity，也不持有数据库连接。
- `app/controler/runtime.py`：复用共享 `GitHubApp` 和数据库，只增加后台同步任务，
  由已有 `_tasks` 负责停机取消及等待；保留当前维护和控制台相关改动。
- `app/controler/events/router.py`：只调整触发标签名称的大小写比较，不在数据库事务内联网。
- 测试与文档：扩展标签相关测试，增加后台扫描合同验证；收窄更新 `README.md`、
  `docs/deployment/README.md`、`docs/architecture/github-app.md` 和 changelog，
  将“人工预建”改为自动创建的范围、时机、权限要求及失败诊断。

API 依据：[App installation 枚举](https://docs.github.com/en/rest/apps/apps#list-installations-for-the-authenticated-app)、
[installation 仓库枚举](https://docs.github.com/en/rest/apps/installations#list-repositories-accessible-to-the-app-installation)、
[Labels API](https://docs.github.com/en/rest/issues/labels#create-a-label)。
实施时核对锁定的 githubkit 0.16 API 签名与实际响应字段，不凭记忆推断。

### 备选方案与取舍

- **仅在第一次触发时创建：** 触发本身依赖标签已存在，无法解决首次使用的问题。
- **只处理 Flow 或 Projects 已记录的仓库：** 覆盖不到首次使用、未配置 Projects 的仓库。
- **安装事件实时初始化：** 响应更快，但需要独立异步处理，仍需启动扫描补偿旧安装和漏投；
  本次采用一条周期扫描路径，接受新仓库可能等待一个周期加扫描耗时。
- **逐个 GET 三个标签：** 实现直接，但通常需要三次查询；选择分页读取仓库标签，
  同时用成功列表响应区分“缺失定义”和“仓库不可读”，避免额外的 404 探测逻辑。
- **持久队列、成功缓存或额外并发：** 标签是否存在可重新读取；先不引入需失效、迁移或恢复的状态。

### 成本、风险与限制

- **作用范围是全部 App 授权仓库。** 只希望使用部分仓库时，应在 App installation 中选择目标仓库；
  本次不会自动收窄安装授权，也不以用户 allowlist 推断仓库所有权。
- 后台扫描增加读取配额，仓库或标签很多时一轮较慢；完整分页、流式处理和限流退避优先于吞吐优化。
  默认周期表示两轮之间的等待，新仓库发现时间还包括实际扫描耗时。
- 权限未授权、仓库暂时不可访问或只读时可能无法创建；明确记录错误并在后续扫描重新尝试，
  不自动申请权限。正在恢复的既有标签 effect 不重写：若此前已被明确拒绝，仍沿用现有人工重试入口。
- 不把“serve ready”描述成“所有仓库标签已建好”。用户需在首轮完成后再选择触发标签，
  日志应能区分创建成功、已有定义和初始化失败。
- 测试只访问替身或 MockTransport，不使用真实 installation token，不创建真实仓库标签。
  本地副本可修改，针对他人仓库的实际共享状态操作仍必须由用户手工执行。

## 2. PR change timeline

### [001] — 2026-10-20 — 未建齐仓库每 300 秒检查，已建齐仓库每天复查

- **需求更新：** 用户明确要求“没有创建过的，每300s一次，已创建的每天一次”。
  按仓库区分频率：三个当前配置标签全部被确认存在才算已建齐，人工预建的标签也计入。
  只建好其中一部分、首次尚未确认或上次检查失败的仓库，仍走 300 秒检查路径。
- **行为决定：** 首次发现时立即检查；尚未建齐的仓库每 300 秒读取并补齐缺失项。
  一次成功确认三个标签齐全后，下次检查设为 24 小时后，即 86400 秒后，
  不按香港时区的午夜统一执行。未到期的已建齐仓库不读取标签，更不发送标签写入请求。
  每日复查发现缺失时当次补建；全部补齐后继续每日检查，读取或创建失败则恢复 300 秒重试。
  遇到更长的 Retry-After 时不得为了满足常规周期提前请求。
- **发现与检查分开：** App 安装和授权仓库的发现仍每 300 秒进行，
  已建齐仓库继续出现在授权清单中，但跳过未到期的标签检查。
  这两个频率不再跟随 PR 的 `reconcile_interval_seconds` 改动；本次不新增频率配置项。
  实现按各自到期时间安排检查，避免因固定 300 秒轮询错过刚到期的任务后再多等一个完整周期。
- **持久化设计（拟议）：** 在现有 PostgreSQL 中增加一张本功能专用的最小检查时间表，
  按 App、installation、规范化仓库身份关联当前三个角色标签名和下一次检查时间。
  成功保存下一次时间为完成确认时刻加 86400 秒，失败保存为失败时刻加至少 300 秒，
  重启后沿用该时间，不把已确认仓库重新当作首次处理；配置名称或安装身份变化则重新确认。
  保存标签名本身即可，不额外引入哈希格式、逐标签状态、历史记录、通用队列或任务租约。
  检查时间记录不授予仓库访问权；每次仍以 App 当前授权发现结果决定是否处理，
  不凭历史记录访问已移出授权范围的仓库，也不因一次枚举失败就清除全部已确认记录。
- **取舍：** 纯内存时间表更小，但重启后会重新检查全部已有仓库，无法跨重启保持每日频率。
  为保留每日间隔，拟新增 `app/persistence/labels.py` 中的具体仓储及 schema 中的一张表；
  只保存可重建的调度检查点，不保存持久仓库清单。数据库错误不记作确认成功，后续恢复再检查。
  此项覆盖初始方案“无新表、无成功缓存”的限制，保留其余权限、只补缺失和失败隔离边界。
- **影响与限制：** 已建齐仓库的标签若被删除，在没有其他操作的情况下可能等到下一次每日检查
  才补回；正常情况下最长约 24 小时，网络、限流或维护暂停可能更久。
  原有工作流标签 effect 的失败诊断和重试入口保留，不增加额外高频读取来绕过每日检查规则。
- **拟验证：** 使用受控时钟验证混合仓库的 300/86400 秒边界、未到期零标签请求、
  重启保留时间、自定义标签名变化失效、人工预建后转每日、每日补建成功及失败退回 300 秒，
  以及跨重启的 Retry-After；覆盖发现请求失败不会误清已确认记录。
  新增检查点消融：临时移除重启恢复，确认重启后提前检查的合同测试失败，恢复后通过。
- **状态与覆盖关系：** 这是用户要求的频率修订，实施与整份详细方案审批仍待完成。
  本条覆盖初始计划第 4 项统一 300 秒扫描、无检查状态表/成功缓存，以及对应技术和验证选择；
  初始方案原文保留作比较基线，以本条修订为准。本轮只更新计划及索引，未修改实现或测试，
  未执行新功能测试，未提交、推送或访问真实 GitHub 写入接口。
