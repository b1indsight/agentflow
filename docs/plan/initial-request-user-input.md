# 首次编码请求用户回应

阶段：方案待确认。

## 首次编码的两个结束动作

现有 `open_pr` 回执证明的是 PR 交付意图；一次普通 MCP 调用（如 `search_flows`）不会生成它。建议给 INITIAL 加 `request_user_input(question: str)`，只记录要问用户的问题并返回确认，不创建 PR、不发 GitHub 评论，也不让 worker 进程阻塞等回复。此阶段沿用当前首次编码必须有已推送提交的前提。

## 最小实现范围

1. 在 worker 的 MCP 注册、工具权限和首次/纠错提示中提供新工具。要求问题非空。一次 INITIAL 只能选择一个结束动作；调用失败和只调用查询工具仍不算完成。
2. 在同一执行上下文记录成功的请求。终态结果携带独立的用户问题（不要填充 `open_pr_call_id` 或伪造 `DeliveryReceipt`）。保留已有 VCS 和 assignment 核验；正常 `open_pr` 仍走原来的回执校验。
3. Control 在接收已绑定的 INITIAL 终态时持久保存问题、session、分支和 head，完成 Job、进入 `review`。问题可以随终态结果一同入库，无须在工具调用时再向 GitHub 或数据库写一次。无 PR 路径不运行开 PR、reviewer 和 `on_pr_opened`。在详情显示问题，并区分无 PR 待回应与已有 PR 待审核。

本次不改用户回复后的派发、修订准备或 GitHub 评论入口。若要在提交前请求澄清，需要另行定义无提交的暂停结果，不能沿用这里的 VCS 前提。

## 验收

走真实 INITIAL 终态链路验证：调用新工具后，Job 完成、用户能看到问题、Flow 停在审核且无 PR；相同终态重放不会二次派发。对照 `open_pr`、只查询、工具失败和未推送四种结果；仅原有 PR 路径产生 PR 操作。拒绝同一次执行提交互相冲突的结束动作。

## 变更记录

### 2026-11-24：暂停表示待用户处理，不要求答复

本条替代初始方案中 `request_user_input(question)` 的接口、展示和验收措辞。工具改为 `request_user_action(action: str)`；`action` 是给用户看的处理事项，例如“请在测试环境验证登录流程”，不要求写成问题。调用成功即结束本轮编码，Flow 进入 `review`，控制台显示“待用户处理”和事项正文。即使用户不发消息，也能保持暂停；不以收到回复为结束本轮的条件，不新增答复框或自动续跑。验收使用一条无需文字回复的处理事项，其余开 PR 分支及 VCS 前提不变。

### 2026-11-24：复用编码主路径和现有消息入口

最终接口为 `request_user_input(message)`。工具是本轮编码的最后一个业务动作：Worker 继续执行正常终态校验，Control 在同一结果事务里保存待处理说明、会话和已推送的提交。无需创建等待 Job，也不保持编码进程运行。

待处理期间，任何经现有授权入口收到的内容（包括受委托工作的结果）沿用同一输入队列。新 Job 仍是 INITIAL，绑定同一个 Attempt、workspace 和编码会话，既可再次暂停，也可打开 PR。没有输入就保持审核；前端沿用原有成功或废弃归档。此改动不创建 agent 间通信端点，不授权其他 worker 访问 owner API，不负责派生子 Flow。
